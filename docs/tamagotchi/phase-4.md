# เฟส 4: Async PvP

ภาพรวมทั้งหมดดูที่ [roadmap.md](./roadmap.md) · เฟสก่อนหน้า: [phase-3.md](./phase-3.md)

> **สถานะ: ✅ ทำแล้วทั้ง 4a และ 4b** (รวมใน PR เดียวต่อ repo) ตัดสินใจตามข้อเสนอทุกข้อ ดู "ตัดสินใจแล้ว" ท้ายเอกสาร และ "ผลที่ทำจริง" ที่บอกส่วนที่ต่างจากแผน

หลักการจาก roadmap: สู้กับ **snapshot** ของผู้เล่นอื่น (ไม่ต้องออนไลน์พร้อมกัน), ELO, ซีซันรายเดือน, **ห้ามใช้ตัวเช่า** (เฟส 5) PvP ใช้เฉพาะมอนที่มีชีวิตของตัวเอง จึงห้ามตัวเช่าโดยปริยาย

แบ่งเป็น 2 PR:

| ส่วน | เนื้อหา |
|---|---|
| **4a** | ทีมป้องกัน (snapshot), เรตติ้ง ELO, จับคู่คู่ต่อสู้, ต่อสู้, ประวัติ + replay, คู่ต่อสู้ NPC |
| **4b** | ซีซันรายเดือน (เปลี่ยนซีซันแบบ lazy ไม่มี cron), อันดับ, รางวัลซีซัน |

## ขอบเขต

**ทำในเฟสนี้**
- ตั้ง **ทีมป้องกัน** = snapshot ของมอนตัวปัจจุบัน (ค่าพลังรวมอุปกรณ์ ธาตุ สกิล) ไว้ให้คนอื่นท้า
- ท้าคู่ต่อสู้ 1 ใน 3 ที่เซิร์ฟเวอร์เสนอ ต่อสู้ด้วยค่าพลัง **สด** ของมอนตัวเองกับ snapshot ของอีกฝ่าย ใช้ `simulateBattle` เดิม (seed + event log) ผลเดิมทุกครั้ง
- ELO ต่อซีซัน, ประวัติการท้า/ถูกท้า, replay ย้อนหลัง
- คู่ต่อสู้ NPC เติมเมื่อผู้เล่นจริงไม่พอ
- ชื่อแสดงในสนามเป็น **ชื่อสนามที่ผู้เล่นตั้งเอง** ไม่เปิดเผย username (ดู PDPA ด้านล่าง)

**ยังไม่ทำ**
- Realtime ท้าเพื่อนสด (เฟส 6) ใช้ `simulateBattle` และ ELO ชุดเดียวกันต่อยอดได้
- Raid Token เป็นรางวัลซีซัน (เฟส 5) ตารางรางวัลเป็นข้อมูล เพิ่มสกุลทีหลังได้
- Push notification เมื่อถูกท้า (หัวข้อ 12 ใน roadmap) เฟสนี้ดูได้ในประวัติตอนเข้าเกม

## กติกา (backend `src/modules/monster/`)

ค่าอยู่ใน `monster-rules.ts` เผยแพร่ผ่าน `GET /monster/wiki` ตามเดิม ลอจิกล้วนเป็น pure function (`elo.ts`, `pvp-matchmaking.ts`, `pvp-season.ts`) มี spec

### ทีมป้องกัน (snapshot)

- `POST /pvp/defense` เก็บ `IFighter` จากมอนที่มีชีวิตและฟักแล้ว คำนวณด้วย `toFighter(state, gear)` โดยบังคับ **stamina เต็ม** (ผู้ป้องกันไม่ถูกลงโทษเพราะไม่ได้ออนไลน์) พร้อมชื่อสปีชีส์/emoji/ร่าง
- ต้องตั้งทีมป้องกันก่อนถึงจะท้าได้ กันคนท้าอย่างเดียวโดยไม่เสี่ยงอะไร
- ตั้งใหม่ได้แต่มี cooldown 30 นาที กันเลือกทีมป้องกันหลังเห็นรายชื่อคู่ต่อสู้ มอนตายแล้ว snapshot ยังอยู่จนกว่าจะตั้งใหม่ (เป็น "snapshot" ตามชื่อ)
- มีได้ 1 ทีมต่อผู้ใช้ (`pvp_defenses` unique `user_id`)

### เรตติ้ง ELO (`elo.ts`)

- เริ่ม 1000, ขั้นต่ำ 0 `expected = 1 / (1 + 10^((Rb − Ra)/400))`
- ผู้ท้า K = 32, ผู้ป้องกัน K = 16 (ถูกท้าเสียน้อยกว่า ไม่ให้การไม่ออนไลน์ถูกลงโทษหนัก)
- ผลคิดจากเซิร์ฟเวอร์เท่านั้น client ส่งแค่ `opponentId`

### จับคู่ (`pvp-matchmaking.ts`)

- `GET /pvp/opponents` เสนอ 3 คน จาก snapshot ของผู้เล่นอื่นที่ **ร่างเดียวกัน** (ร่างโต / สมบูรณ์ / สูงสุด) เรียงจากเรตติ้งใกล้ที่สุด ไม่เกิน ±600 (แผนเดิมเขียน "ขยายหน้าต่างทีละ 100" ซึ่งให้ผลเท่ากับเลือกคนใกล้สุดภายใน ±600 จึงทำแบบหลัง)
- ไม่เสนอคนจริงที่ท้าไปแล้วครบ 2 ครั้งในวันนี้ และไม่เสนอตัวเอง (ข้อจำกัดนี้ใช้กับคนจริงเท่านั้น NPC ท้าได้ไม่จำกัดเพราะมีเพดาน 10 ครั้ง/วันอยู่แล้ว)
- **ต้องเป็นร่างโตขึ้นไปถึงเข้าสนามได้** (ไข่/ร่างเด็กเข้าไม่ได้ ค่าพลังห่างเกิน)
- เติมด้วย **NPC** ให้ครบ 3 คน (`PVP_NPC_RIVALS` เป็นข้อมูล: ชื่อ ธาตุ ร่าง เรตติ้งคงที่ ค่าพลังจากตารางสปีชีส์) ผู้ท้าได้/เสียเรตติ้งปกติ NPC ไม่มีเรตติ้งเปลี่ยน
- `POST /pvp/battle { opponentId }` เซิร์ฟเวอร์ตรวจซ้ำว่า `opponentId` อยู่ในหน้าต่างและเงื่อนไขเดียวกัน ไม่ใช่ id ที่ client ปั้นเอง

### ต้นทุนและกันโกง

- ต้นทุนเหมือน PvE: stamina −10, น้ำหนัก −1 ใช้ไม่ได้ถ้าป่วย/ออกสำรวจ (`assertCanBattle` เดิม) **ไม่นับ `wins`/`losses` ของมอน** เพื่อไม่ให้เงื่อนไขวิวัฒนาการร่างสูงสุด (ชนะ ≥ 5) ถูกปั๊มผ่าน PvP (เรตติ้งนับแยกใน `pvp_ratings`)
- ท้าได้วันละ 10 ครั้ง (นับวันตามเวลาไทยเหมือนภารกิจ) นับจาก `pvp_battles` หลังล็อกแถวมอน คำขอซ้อนกันของผู้ใช้เดียวจึงต่อคิว ใช้เกินไม่ได้
- รางวัลคงที่ต่อครั้ง: ชนะ 🪙 15, แพ้ 🪙 3 (จ่ายด้วย reason `pvp_reward`) เพดานรวมจึงตายตัวจากเพดานครั้ง/วัน
- ป้องกันเลี้ยงเรตติ้งผ่านบัญชีรอง: จับคู่ตามเรตติ้ง + ร่างเดียวกัน, คนเดิมท้าได้ไม่เกิน 2 ครั้ง/วัน, เรตติ้งที่ได้ลดลงเมื่อคู่ต่อสู้เรตติ้งต่ำกว่ามาก (ELO ทำอยู่แล้ว) ไม่มีเงินจริงในเกม ความเสี่ยงต่ำ ไม่ต้องตรวจจับพิเศษ

### ซีซัน (4b, `pvp-season.ts`)

- ซีซัน = เดือนปฏิทินเวลาไทย (`YYYY-MM`) ใช้ตัวช่วยวันที่เดียวกับภารกิจ
- **ไม่มี cron:** แถวเรตติ้งแยกตามซีซัน (`pvp_ratings` unique `(user_id, season)`) การต่อสู้ในซีซันใหม่เขียนแถวใหม่ แถวซีซันก่อนจึงหยุดเปลี่ยนเอง
- แถวใหม่เริ่มจาก soft reset: `1000 + (เรตติ้งซีซันก่อน − 1000) × 0.5`
- **รางวัลซีซัน:** `POST /pvp/season/claim { season }` รับได้เฉพาะซีซันที่จบแล้ว อันดับคำนวณตอนรับจากจำนวนคนที่เรตติ้งสุดท้ายสูงกว่าในซีซันนั้น (ข้อมูลหยุดเปลี่ยนแล้ว จึงนิ่ง) ต้องสู้อย่างน้อย 5 ครั้งในซีซัน รับด้วย `UPDATE ... WHERE reward_claimed_at IS NULL` ครั้งเดียว ส่งคำขอซ้อนได้รางวัลครั้งเดียว (แบบเดียวกับรับภารกิจ)

| อันดับ | รางวัล (เฟส 5a เพิ่ม 🎖️ Raid Token) |
|---|---|
| 1 | 🪙 1,000 + 💎 30 + 🎖️ 20 |
| 2–3 | 🪙 600 + 💎 20 + 🎖️ 12 |
| 4–10 | 🪙 300 + 💎 10 + 🎖️ 6 |
| ผู้เข้าร่วม (≥ 5 ครั้ง) | 🪙 100 + 💎 3 + 🎖️ 2 |

## ความเป็นส่วนตัว (PDPA)

- อันดับและประวัติ **ไม่แสดง username หรืออีเมล** แสดงเฉพาะ `display_name` ที่ผู้เล่นตั้งเองตอนตั้งทีมป้องกัน (ค่าเริ่มต้น `ผู้ฝึก#xxxx` จาก hash ของ user id) พร้อม emoji/ชื่อสปีชีส์
- `display_name` ตรวจความยาว 2–16 ตัวอักษรและ trim ก่อนเก็บ ไม่รับ HTML (frontend แสดงเป็นข้อความธรรมดาอยู่แล้ว)
- API ไม่คืน `user_id` ของผู้อื่น: คู่ต่อสู้อ้างด้วย `opponentId` ที่เป็น id ของแถว `pvp_defenses` ไม่ใช่ id ผู้ใช้
- snapshot และ `pvp_battles` เก็บเฉพาะค่าพลังเกม ไม่มีข้อมูลส่วนบุคคลอื่น

## ความปลอดภัยของข้อมูลและการล็อก

- ต่อสู้ทั้งหมดอยู่ใน DB transaction เดียว: ล็อกแถวมอนผู้ท้า → ตรวจกติกาและโควตารายวัน → ล็อกแถวเรตติ้งของทั้งสองฝ่าย **เรียงตาม `user_id`** (กัน deadlock เมื่อ A ท้า B ขณะ B ท้า A) → จำลองการต่อสู้ → อัปเดตเรตติ้งทั้งสอง → จ่ายรางวัล → บันทึก `pvp_battles`
- seed ใช้ `crypto.randomInt` เหมือน PvE เก็บ seed + snapshot ทั้งสองฝั่งในประวัติ เพื่อจำลองซ้ำเป็น replay ได้โดยไม่ต้องเก็บ event log

## API (ทุก route ใช้ `@AuthUser()`)

| Method | Path | Body | ผล |
|---|---|---|---|
| GET | `/pvp` | – | ซีซัน + เวลารีเซ็ต, เรตติ้ง/อันดับ/แพ้ชนะ, ทีมป้องกัน, ครั้งที่เหลือวันนี้, เวลาตั้งทีมได้อีกครั้ง |
| POST | `/pvp/defense` | `{ displayName? }` | `{ defense }` |
| GET | `/pvp/opponents` | – | `{ opponents: [{ id, displayName, emoji, name, stage, element, stats, rating, isNpc }] }` |
| POST | `/pvp/battle` | `{ opponentId }` | `{ monster, battle: { won, rounds, events, player, enemy, reward }, rating: { before, after }, wallet }` |
| GET | `/pvp/history` | – | ล่าสุด 20 รายการ ทั้งท้าและถูกท้า (เห็นว่าใครท้าเรา ด้วยชื่อสนาม) |
| GET | `/pvp/history/:id/replay` | – | จำลองซ้ำจาก seed ได้ `events` |
| GET | `/pvp/leaderboard` | `?season=` | 20 อันดับแรก (ชื่อสนาม, emoji, เรตติ้ง) *(4b)* |
| POST | `/pvp/season/claim` | `{ season }` | `{ wallet, tier }` *(4b)* |

## ข้อมูล (migration `1790700000000-add-pvp` ตัวเดียว ครอบทั้ง 4a และ 4b)

```
pvp_defenses  { user_id unique, display_name, fighter jsonb, stage, species_id, set_at }
pvp_ratings   { user_id, season, rating, wins, losses, reward_claimed_at }   unique (user_id, season)
pvp_battles   { season, attacker_id, defender_id null, opponent_id, attacker_name, defender_name,
                seed, attacker jsonb, defender jsonb, won,
                attacker_rating_before/after, defender_rating_before, defender_rating_after null }
```

- `opponent_id` คือ id แถวทีมป้องกันหรือ id ของ NPC ที่ผู้ท้าเลือก ใช้นับจำนวนครั้งต่อคู่ต่อสู้ต่อวัน (แผนเดิมมี `npc_id` และ `power` ซึ่งไม่จำเป็น)

- `wallet_transactions` เพิ่ม reason `pvp_reward`, `pvp_season_reward`
- `monster_logs` ชนิด `battle` เดิมใช้ต่อ (payload `mode: 'pvp'`) ภารกิจ "ชนะการต่อสู้" จึงนับชัยชนะ PvP ด้วยโดยไม่แก้โค้ด

## ทดสอบ

- `elo.spec.ts`: ชนะคนเรตติ้งสูงได้มากกว่า, ผลรวมสองฝั่งเมื่อ K เท่ากันเป็นศูนย์, ขั้นต่ำ 0, K ต่างกันตามบทบาท
- `pvp-matchmaking.spec.ts`: หน้าต่างขยายตามจำนวนคน, ไม่เสนอตัวเอง/คนที่ท้าครบ 2 ครั้ง/ต่างร่าง, เติม NPC ให้ครบ 3, ไม่ซ้ำ
- `pvp-season.spec.ts`: ขอบเดือนตามเวลาไทย, soft reset, ระดับรางวัลตามอันดับและเกณฑ์ขั้นต่ำ
- สมดุล: ร่างเดียวกันเรตติ้งเท่ากันได้ผลใกล้ 50/50 (รันหลาย seed) และ NPC ของแต่ละร่างชนะได้ด้วยมอนที่เลี้ยงปกติ
- ทดสอบกับ Postgres จริง (ต้องมี DB): ท้าพร้อมกัน 12 request เหลือโควตา 10 ผ่านพอดี 10 · A ท้า B กับ B ท้า A พร้อมกันไม่ deadlock · รับรางวัลซีซันพร้อมกันได้ครั้งเดียว · ซีซันใหม่ soft reset ถูก · ไม่มี endpoint ไหนคืน `user_id`/`username` ของผู้อื่น
- ย้ายสคริปต์ทดสอบ DB ที่ใช้ในเฟส 2–4 เข้า repo เป็น integration spec (ตอนนี้ยังอยู่นอก repo ยังไม่ได้ทำ)

## ผลที่ทำจริง

- **สมดุล NPC:** ความแรงของ NPC ปรับด้วยการจำลองจนมอนที่เลี้ยงดีธาตุเดียวกันชนะราว 75% / 50% / 25% ต่อ NPC เรตติ้ง 900 / 1000 / 1100 (ร่างโต ×1.15 / 1.2 / 1.25 · ร่างสมบูรณ์และสูงสุด ×1.2 / 1.225 / 1.275 ของค่าฐาน) ค่าเริ่มต้น ×1.0 ที่ใช้ตอนแรกอ่อนเกินไป (ชนะ 100%) และผลไวมาก ค่าต่างกัน 0.1 เปลี่ยนจากชนะเกือบทุกครั้งเป็นแพ้เกือบทุกครั้ง ล็อกไว้ด้วย `pvp-data.spec.ts` (มอนร่างเดียวกันเจอกันเอง 40–60%)
- **ธาตุมีผลมาก:** ตารางธาตุ (×1.3 / ×0.8) ทำให้แมตช์ต่างธาตุเอียงมากกว่าส่วนต่างเรตติ้ง NPC ธาตุ ใบไม้/วารี/เพลิง เรียงตามเรตติ้ง 900/1000/1100 ยังเป็นค่าเริ่มต้น ถ้าอยากให้เรตติ้งสะท้อนความแรงจริงให้ปรับธาตุของ NPC ต่อร่าง
- **ทดสอบกับ Postgres จริง** (migration `1790700000000` ผ่าน): ท้าพร้อมกัน 14 request เหลือผ่านพอดี 10 · A↔B ท้ากันพร้อมกันไม่ deadlock (ล็อกแถวเรตติ้งเรียงตาม `user_id`) · รับรางวัลซีซันพร้อมกัน 5 request จ่ายครั้งเดียว · อันดับ 1 ได้ 1,000 🪙 + 30 💎 อันดับ 2 ได้ 600 · ซีซันใหม่ soft reset 1200 → 1100 · คู่ต่อสู้ที่ปั้น id เอง/ต่างร่าง/ตัวเอง ถูกปฏิเสธ · ทีมป้องกันเริ่มต้นไม่ใช้ username · ประวัติ/อันดับ/รายชื่อคู่ต่อสู้ไม่มี `user_id` หรือ `username` ของผู้อื่น · การท้าไม่เปลี่ยน `wins`/`losses` ของมอน
- **Bug ที่เจอจากการทดสอบกับ DB จริง:** `setDefense` อ่านสถานะกลับผ่าน connection อื่นก่อน commit จึงได้ `defense: null` (แก้เป็นอ่านหลัง transaction) และ SQL จับคู่ใช้พารามิเตอร์ทศนิยมกับจำนวนเต็มปนกันจนพัง (ใส่ cast)
- **Stamina ฟื้นเอง** (เพิ่มระหว่างเฟสนี้): แทนการลดเองตามเวลาเดิม ปิดเกม 0.5/นาที เปิดเกม 1.0/นาที ดู [phase-2.md](./phase-2.md) หัวข้อ Stamina ทำให้ท้า PvP วันละ 10 ครั้ง (−10 ต่อครั้ง) รองรับได้ด้วยการฟื้นเองราว 3 ชม. 20 นาที
- **ข้อจำกัดที่ยอมรับ:** อันดับในหน้าจัดอันดับนับผู้ที่สู้อย่างน้อย 1 ครั้ง แต่อันดับรับรางวัลนับเฉพาะผู้ที่สู้ ≥ 5 ครั้ง ตัวเลขอาจต่างกันเล็กน้อย การคำนวณอันดับใช้ `COUNT` ตอนเรียก (ไม่ใช่ตารางจัดอันดับสำเร็จรูป) เหมาะกับผู้เล่นหลักร้อย ถ้ามากกว่านั้นควรเก็บอันดับสุดท้ายตอนซีซันจบ

## ตัดสินใจแล้ว (ตามที่เสนอ)

1. NPC เติมคู่ต่อสู้ เรตติ้งคงที่ ✅
2. จับคู่เฉพาะร่างเดียวกัน และต้องร่างโตขึ้นไป ✅
3. ผู้ป้องกันเสียเรตติ้งด้วย (K=16) ✅
4. ชื่อสนามที่ผู้เล่นตั้งเองแทน username ✅
5. PvP ไม่นับ `wins`/`losses` ของมอน ✅
6. ท้าวันละ 10 ครั้ง · ชนะ 🪙 15 แพ้ 🪙 3 · รางวัลซีซัน 1,000/600/300/100 🪙 และ 30/20/10/3 💎 ✅

## (เดิม) ที่ต้องยืนยันก่อนเริ่ม

1. **NPC เติมคู่ต่อสู้:** แอปนี้ผู้ใช้น้อย ถ้าไม่มี NPC สนามจะว่างเปล่า ตกลงตามที่เสนอ (NPC เรตติ้งคงที่ ไม่เปลี่ยน) ไหม
2. **จับคู่เฉพาะร่างเดียวกัน** และต้องร่างโตขึ้นไป หรืออยากให้จับตามเรตติ้งอย่างเดียว (ผู้เล่นน้อยจะได้คู่ง่ายกว่า แต่ร่างต่างกันมากสู้ไม่สมดุล)
3. **ผู้ป้องกันเสียเรตติ้งด้วย** (K=16) หรือให้เปลี่ยนเฉพาะผู้ท้า (ลงโทษคนไม่ออนไลน์น้อยกว่า แต่ผู้ป้องกันที่แข็งแกร่งไม่ได้ขึ้นอันดับจากการป้องกัน)
4. **ชื่อสนาม (`display_name`)** ที่ผู้เล่นตั้งเอง แทน username ตามหลัก PDPA เหมาะไหม
5. **PvP ไม่นับ `wins`/`losses` ของมอน** (ไม่ช่วยวิวัฒนาการ) ตามที่เสนอ หรืออยากให้นับ
6. ตัวเลข: ครั้ง/วัน 10, รางวัลชนะ 15 / แพ้ 3, ตารางรางวัลซีซัน
