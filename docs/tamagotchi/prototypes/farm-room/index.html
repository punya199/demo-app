Backend proposal: separate furniture queue

  1. Cause: craft_jobs has one unique partial index on user_id (claimed_at IS NULL), and both craft.service.ts and farm.service.ts read it through an unfiltered findActiveJob. So one slot is shared and each side blocks the other.
  2. Schema: add kind varchar NOT NULL DEFAULT 'equipment' to craft_jobs. Backfill 'furniture' where recipe_id LIKE 'farm\_%'. Replace the index with a unique partial index on (user_id, kind). down reverses it, and fails if a player holds two active jobs.
  3. Code: both findActiveJob helpers add kind to the filter. Each save sets its kind. startUpgrade and start then conflict only with their own kind. Remove queueBusy from IFarmView and the front-end type and alert. canStart checks only the furniture slot.
  4. Risk: a job in flight at deploy time keeps working (its kind is derived from the recipe id). Numbers, recipes and times are untouched. Existing specs that assert the shared-queue conflict change to assert the separate slots.
